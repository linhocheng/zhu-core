規則：宣告「修好了」之前，先指出**那個只有修好才會出現的信號**，然後確認真的看到它。一個信號如果「修好了會出現、沒修好也會出現」，它就是零資訊——拿它當證據是在挑對自己有利的解讀。

**Why**：2026-07-02 podcast-worker CPU throttle 修法（保持 HTTP request open）。測試腳本回 `HeadersTimeoutError`，我當場解讀成「這正是修法生效的證明——worker 在生成期間不回 headers」。但這個錯誤**同樣相容於**「任務卡死永遠不會回」。真正的鑑別信號是 Firestore `status=scripted` + worker log 的 `done` 行——去查，兩個 2500 字任務全卡 `running`、container 半途被換掉，修法根本無效。差一步就跟 Adam 說「修好了」。

**心態**：剛部署完自己的修法，看到任何新信號都會想往「生效了」解讀——這是展示衝動的變體（想快點讓修法成立）。越是自己剛寫的修法，越要用敵意讀信號。

**How to apply**：驗證前先寫下一句話：「如果修好了，我會看到 X；如果沒修好，我會看到 Y」——X 必須是失敗時**不可能出現**的（例：目標狀態寫進 DB、log 出現完成行、產出檔案存在且內容對）。timeout、無回應、連線錯誤這類信號幾乎永遠兩邊相容，一律不算數。

**觸發信號**：心裡冒出「這正好證明…」「這就是…生效的表現」而那個信號是 timeout/錯誤/沉默類；剛部署完自己的修法在讀第一個測試結果的時候。

**家族**（驗證失守的三張臉，互補）：[[沙推不是驗證，動手前先驗模型/工具假設]]＝太有把握所以沒驗；[[標了風險不等於驗了風險]]＝標了但跳過驗；本條＝**驗了，但拿不具鑑別力的信號當證據**。第三張最隱蔽——你自以為驗證流程走完了。
