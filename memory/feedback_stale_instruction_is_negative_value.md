**規則**：記憶的過期分兩級。**知識過期是零值**（「Cloud Run 用 cert(sa) 會死」錯了就只是錯了，它不會叫我去做什麼）。**指令過期是負值**——給現成可貼指令的記憶，過期後比沒有記憶更糟，因為它**穿著天條的外衣繼續下令**。

**Why**：2026-08-06 全庫診斷撞出兩條有害記憶——

1. `feedback_killall_vs_pkill` 的 How to apply 給了一整條可貼指令：`killall -9 node ... && nohup node index.js &`。但 bridge 早已由 systemd 接管，照做會起**兩個 process**。那正是 MOLOWE 產出 4 篇而非 2 篇的事故根因——事故當時沒人想到根因是一條「格式完整、有 Why 有心態、看起來很好的記憶」。
2. `reference_cloudrun_background_task_sop` 檔頭疊了**兩層**「已退役」補丁，正文照舊完整教 `--min-instances=1`。補丁擋不住掃讀——**掃讀的人看到程式碼區塊就複製**。

**心態**：過期記憶不會自己舉手。它不會變得可疑，它會變得**更權威**——因為它躺得越久，被引用的次數越多，看起來越像共識。對「格式最完整、寫得最好」的那幾條要特別警覺，那是最容易被照抄的。

**How to apply**：
- **推翻舊解法時動正文，不准只在檔頭加補丁。** 補丁只擋得住從頭讀的人，擋不住掃讀的人（掃讀才是常態）
- **給指令的記憶必須先寫「判準」再寫「指令」**。範例：`reference_cloudrun_background_task_sop` 重寫後開頭第一句是「先分類：這台機器閒著時，有沒有人可能下一秒需要它？」，指令排在判準後面
- 引用任何記憶裡的**可貼指令**之前，先確認那個環境的現況（有沒有 process manager？服務還在不在？旗標名還一樣嗎？）
- 發現某條記憶的指令已失效：**當場改，不要留給下一個自己**。下一個我會直接貼

**觸發信號**：正要複製記憶裡的一段 shell／程式碼直接執行；看到某條記憶檔頭有「已退役／已升級／⚠️」但正文還在教舊做法；心裡冒出「這條寫得真完整」。

**家族**：[[feedback_memory_can_lie]] 是總則（記憶會說謊），本條是**最危險的那一種謊**——會叫我動手的謊。[[feedback_capacity_constants_expire]] 是它的數字版。
