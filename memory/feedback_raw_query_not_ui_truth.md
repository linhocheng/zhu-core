**規則**：回報「用戶會看到什麼」之前，必須走跟 UI 同一條讀路徑（產品 API / 帶過濾的 lib 函數）。debug script 直撈原始層查到的東西，只能以「原始層資料」的名義呈現，不能翻譯成 UI 行為。

**Why**：原始層看得到的，業務層不一定放行。2026-07-24 UDN：我用 raw Firestore query 列角色（含 archived 的 Alex），回報 Adam「四位角色的聲音都能選」；實際 `/api/characters` 過濾 archived 後只有三位。我的錯誤回報變成 Adam 的假警報（「Alex 移除了還在，是 bug？」），查完發現 bug 是我的話不是系統。

**心態**：debug 求快直撈沒有錯，錯在把「我查到的」無標籤地說成「你會看到的」。兩個層級之間永遠隔著一層業務規則。

**How to apply**（2026-08-07 動作化升級）：

- 任何寫給 Adam 的「用戶會看到 X」，**貼的必須是產品 API 的回傳原文**（同 auth、同過濾）。貼不出來就不能用「會看到」這個說法
- debug script 的輸出**一律前綴層級標籤**：`[原始層,含已封存]`／`[產品層]`。沒標籤的輸出不准進回報
- 原姿態版（聽到自己說「都能選」→ 問這是哪一層的「都」）留作理由：那一問要靠聽見自己，貼原文是機械動作

**入口層變體（2026-08-08 threads-radar，同型三犯後補）**：篩選／搜尋／導覽這類功能，
「查得到」和「點得到」是**兩個獨立的層**，資料層綠燈不代表入口存在。
- 動作：修完任何篩選/入口功能，**必答兩題**——①這個入口（按鈕/選項/連結）是**誰產生的**？
  ②它的來源跟資料的來源**同源嗎**？答不出來就還沒驗完，不准說「修好了」。
- 不同源＝必然分裂：threads-radar 的篩選按鈕讀 `keywords`（我現在設定的字），
  貼文池讀歷史收過的全部——關鍵字一刪，55 篇沒按鈕可篩、10 篇 UI 完全觸及不到
  （含全庫第二高讚的爆文）。我用 REST 打 `?kw=行銷` 撈到 11 篇就宣告「點行銷撈得到」，
  **那顆按鈕根本不在畫面上**。
- 同場還有一層：未登入 curl 回 307 只證明鎖有效，**根本沒跑到渲染**——
  307 在「頁面正常」和「頁面會 500」兩種情況下長得一模一樣，不能當渲染層驗證。

**觸發信號**：正要把 DB query 結果寫進給 Adam 的回報；Adam 拿我上一句回報來問「是不是 bug」；
剛修完一個篩選/入口功能，正要說「現在點 X 就看得到了」。
