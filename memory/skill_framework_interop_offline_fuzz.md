包框架的生命週期介面（audio output、lifecycle hook、事件回呼）時，**單元測試全綠只證明「我想像中的框架」下自洽**——框架真實的呼叫順序、路徑數、時序分佈都可能超出想像。

**Why**：2026-07-10 ailivex v18 優雅讓位層（BoundaryAwareAudioOutput 包 LiveKit AudioOutput）。16 個單元測試全綠，四通真實通話**每通撞一個新 bug**：①播放時鐘跨段污染（節流失效）②commit 後狀態重置 resume 被誤當誤觸翻案（74µs 樣本）③對已暫停語音的默殺 commit 路徑（不 clear 不 resume，16 秒黑洞）④遲到 459ms 的狀態重置打臉 0.25s 時間護欄。框架有三條 commit 路徑、六個 pause/resume/clear 呼叫點，我只想像了一條。

**心態**：這是「沙推不是驗證」的第四張臉——前三張是沒驗/標了沒驗/信號零資訊，這張是**驗了，但驗的對手是自己想像的**。測試向量的來源決定測試的效力：自己編的序列＝驗證自洽；真實 log 抽的序列＋任意交錯 fuzz＝驗證前提。

**How to apply**：
1. 動手包之前：grep 框架源碼，窮舉目標介面的**所有**呼叫點（不是文件說的，是 code 裡的）
2. 上線第一通之後：把真實 log 的事件序列（含時間差）抽出來固化成測資
3. 寫 property-based 沙推：任意順序、任意時間差的指令排列去轟，驗證不變式（不掛死/不復播/不阻塞）而非具體行為
4. 時間差護欄是賭博：兩個樣本差四個數量級也不能定閾值（狀態重置 resume 74µs~459ms 都出現過，取決於生成收尾——是分佈不是定值）。分辨信號用**狀態語意**（commit 後一律不翻案）不用時間
5. 真人測試是驗收不是探索：離線全綠才請用戶打一次；拿用戶真通話當 QA 循環＝把發現成本轉嫁給關係

**觸發信號**：準備 override/wrap 框架的 node/output/hook；寫測試時發現序列是「我覺得框架會這樣叫」；連續兩通真實測試各撞一個新 bug（第二通就該停下來轉離線）；想用時間差區分兩種同名信號。
