## delta
進場前以為：交互 UI 功能「build 綠＋離線單元測試過」就能交付、宣稱可用。
現在理解：**瀏覽器表單行為是我工具測不到的盲區**——contentEditable 相鄰元素合併、textarea 送 CRLF、field-sizing 在 Safari 失效，這三個 bug 全是「只有真人在瀏覽器點才會冒出來」。build 綠和 curl 測活體渲染都抓不到。我三輪都在「交付→Adam 當 QA 回報 bug→我才修」的循環裡，讓 Adam 點了三次。
移動原因：第三個 bug（CRLF）查根因時發現，前兩個也同構——都是「輸入層我沒測到的真實行為」。這不是三個孤立 bug，是一個盲區的三張臉。
違背了哪條 feedback：feedback-mvp-include-input-entry（走骨架要含「使用者怎麼把輸入送進去」）的延伸——我做了輸入入口，但沒測「輸入真的送出時會發生什麼」。

## 心法狀態
- 鑑別信號（天條）：W30 用 DB 落地＋計費驗；AIO 用「壞 token 回連結無效」「CRLF 髒資料渲染成 42 段獨立段落」這類只有修好才出現的信號；不拿 build 綠當功能證據
- 收斂點防禦：scanMarkdown 移進 collections 當唯一的稽核尺（客戶改字重掃同一把）；CRLF 正規化也釘那裡→一處修解三處 bug
- 保留原始版本救可逆：originalMarkdown 安全網兩次救回被 corruption 的草稿——寫入型功能必留原稿
- 沒說動手就不動手：憲法區兩次都等 Adam「WAITIN ok」才併；DataForSEO key 等 Adam 給才灌
- 開發不燒付費 key（天條）：AIO live 驗證是 Adam 明確給 key＋說「直接上」才燒的 ~$0.12

## 教訓
### L1：交互 UI 的 verification 不能只靠 build 綠＋離線單元測試
- 現象：客戶編輯器三輪 bug（contentEditable 相鄰合併壓平／textarea 送 CRLF 破壞段落切分／field-sizing Safari 失效裁字），全 build 綠、離線稽核測試過，但一到真人瀏覽器就爆
- 根因：瀏覽器表單送出行為（換行正規化、contentEditable 合併、CSS 特性支援）是 curl/單元測試碰不到的層；我把「編譯過＋渲染對」當成「功能對」
- 下次：交互 UI 要嘛設 headless browser（playwright）測真實 round-trip，要嘛從第一次交付就明說「這條我工具測不到，你必須親手點」——不要等它爆才承認
- 對應 feedback：feedback-mvp-include-input-entry（延伸：不只做輸入入口，要測輸入送出的真實行為）

### L2：寫入型功能一定留原始版本（做對的）
- 現象：客戶編輯 corruption 兩次，都靠當初保留的 originalMarkdown 完整還原，零資料損失
- 心法：任何讓使用者改資料的功能，存原稿當安全網，corruption 才可逆——這次派上用場兩次
- 對應：sync-truth-principle 的預防版
