## 教訓
### L1：「唯讀/零成本」是我對行為的判斷，不是端點給我的保證——付費 API 沒有「查一下」，只有「發一次」
- 現象：查 Veo 允許秒數，文件連兩次抓不到，我想出「送不合法秒數讓 API 吐出允許值」的招，**在訊息裡寫下「零成本探針（無效請求不計費）」——那句話寫在驗證之前**。一個迴圈跑六個值：3/5/7/10 被擋（不計費），**4/6 是合法值，各真的生了一支影片**，燒掉 10 秒 veo-3.1-fast ≈ $1.0-1.5，且是繞過平台預算承重牆的**帳外開銷**
- 根因四層：(1) 同場已錯兩次，戴罪立功狀態急著拿硬證據；(2) 連兩次查證失敗後**升級**手段而不是**降級**成「我不確定/問 Adam」；(3) 三禁三必的反射掛在「改東西」上，沒掛在「查東西」上——分類一錯紀律整條不啟動；(4) 假設單價為零時數量紀律自動蒸發（0×6 還是 0）
- 下次：對外部付費 API 的任何 POST，先問「這一發如果被受理，會不會產生東西」；非同步端點（LRO）**收單就回 operation name，之後才驗參數**——「被接受」是零資訊信號。探針只發一發，等完整結果，確認計費行為，再決定第二發
- 對應 feedback：feedback_no_paid_api_without_consent（違背）＋新建 feedback_probe_cost_assumption_unverified＋feedback_ambiguous_signal_not_proof（202 Accepted 是它的付費版）

### L2：可編輯的欄位如果不通到生成端，重生越多次錯得越深——因為隨機性會偽裝成「有在動」
- 現象：客戶改中文描述、按重生，圖每次都不一樣（gpt-image 本來就有隨機性）但**永遠不照他的改動**。零錯誤 log，五次重生五次收費
- 根因：面談時 LLM 同時產出 desc（給人看）與 promptEn（給引擎），之後 UI 只開放改 desc。設計時假設「兩者會一起被維護」，實際上沒有任何機制保證
- 下次：任何「一份資料兩種表述」的設計（中文/英文、給人看/給機器看），**要嘛同一個編輯動作同時更新兩者，要嘛把不同步狀態顯示在畫面上**。落點：`nextPromptStale` 純函式＋卡面紅字
- 對應 feedback：新承重牆 #6；家族＝sync-truth-principle（後台必同步前台）的輸入端鏡像
