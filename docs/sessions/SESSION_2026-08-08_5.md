## 教訓

### L1：同一個病會長出多張臉，修完一層要主動掃上下游
- **現象**：threads-radar 的「找不到貼文」連續三輪，每輪修完都宣告完成，每輪都被追問出更深一層。
  排序（東西在但沉底）→ 計數（數字說謊）→ 入口（按鈕不存在）。
- **根因**：把「症狀消失」當成「病治好」。第一輪修了排序，症狀（Adam 找不到那篇）確實消失了，
  但造成症狀的機制——「顯示的東西 ≠ 底層實際有的東西」——一層都沒動。
- **下次**：修完任何一層，強制問三句：這層的**資料**從哪來（上游）？這層的**入口**誰產生（下游）？
  這層的**數字**是全量還是視窗？三句都答得出來才收案。
- **對應 feedback**：feedback_solve_root_not_symptom（解決問題還是繞開根本問題）

### L2：「資料查得到」不等於「使用者點得到」——兩層要分開驗
- **現象**：第二輪修完，我用 REST 打 `?kw=行銷` 撈到 11 篇，宣告「點行銷就撈得到」。
  實際上那顆按鈕在畫面上根本不存在——篩選列讀的是使用者當下設定的關鍵字，那個字早被刪了。
- **根因**：REST 直撈驗的是「資料層通不通」，產品真相是「使用者走 UI 那條路徑能不能到」。
  我拿前者的綠燈去宣告後者。
- **下次**：驗任何篩選/入口類功能，除了「查得到嗎」還要問「這個入口是誰產生的、來源是什麼、
  來源會不會跟資料脫節」。入口的來源和資料的來源不同源＝必然分裂。
- **對應 feedback**：feedback_raw_query_not_ui_truth、feedback_interface_blood_vessel_check
