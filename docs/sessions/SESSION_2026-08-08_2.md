## delta
**進場前以為**：Firestore REST PATCH 帶 `updateMask.fieldPaths=X` 就一定只動 X 欄、其他欄受保護——這是我對部分更新語意的默認信任。
**現在理解**：那個 PATCH 的 updateMask 沒生效（原因仍未完全查明），變成整份覆寫，把一個生產 client doc 洗到只剩一個欄位。**單筆生產資料的欄位更新，不能賭 API 的「應該只動這欄」——要嘛先讀出整份備份、要嘛用顯式列全欄位的 mask、要嘛先在非生產驗一次寫入行為**。這是「記憶會說謊」的 API 語意版：我對工具行為的默認信任，跟工具實際行為之間有縫，而生產資料手術正是這條縫最貴的地方。
**移動原因**：親手洗掉 doc，PITR 復原時逐欄重建才痛感到「我以為 updateMask 保護了其他欄」是錯的。同場另一個佐證：本機 build 綠 Vercel 才炸（firebase-admin vs @google-cloud/firestore）——同一條「我以為環境一致」的默認信任裂縫。
**違背的 feedback**：接近違背「動手前先看現場」的資料版——我對 qqc2xTNX 做寫入前，沒有先備份那份 doc 就下 PATCH。看了現場（讀了 doc）但沒有為「寫入可能出錯」預留退路。

## 心法狀態
- 「模稜兩可信號不當成功證據」全場撐著：每個修法（redirect fix／ingest／登入／還原）都先寫「修好會看到 X、沒修好會看到 Y」，PITR 復原也用「6 關鍵字＋session 字數」當絕對值驗，不靠「沒報錯」
- 「防禦釘在收斂點」兩次落地：redirectErr helper（9 處一次修）、poolPostId 去重鍵咽喉
- 新體感：**PITR 是生產資料手術的安全網，但不是免死金牌**——近 1 小時內讀不可靠、7 天窗會過期。真正的安全網是「寫之前先備份/先顯式全欄」，PITR 是最後一道

## 教訓
### L1：生產資料的單筆欄位寫入，先備份整份或顯式列全欄，別賭 updateMask 只動目標欄
- 現象：`PATCH ...?updateMask.fieldPaths=passcodeHash` body 只帶 passcodeHash，結果整份 client doc 被覆寫成只剩 passcodeHash，email/status/schedule 全失。同款 mask 語法在 8/5 改 email 時是好的，這次卻整份覆寫，原因未完全查明。
- 根因：我對「updateMask 會保護未列欄位」是默認信任，沒驗證這條 API 在這個路徑上的實際行為；且下寫入前沒先讀出整份 doc 當備份。生產資料手術的縫就在「我以為工具會 X」。
- 下次：改生產單 doc 前，(1) 先 `GET` 整份存進 scratch 當備份，(2) 寫入用「顯式列出所有 fieldPaths 的 mask」或直接整份 set，(3) 寫完立刻 GET 驗欄位齊全。三步當硬步驟，不省。
- 對應 feedback：feedback_memory_can_lie 的 API 語意版（對工具行為的默認信任＝另一種會說謊的記憶）；與「本機 build 綠 Vercel 炸」同源（環境/工具行為的默認一致性不可信）。

### L2：級聯刪除的價值方向要對齊資產價值，不是對齊資料關聯
- 現象：deleteClientAction 按 clientId 級聯刪 keywords＋threads_accounts。有人刪一個成員，把該成員捐入的「唯一情報帳號＋加密 session」一起帶走——最貴最難重建的東西陪葬，而便宜的爆文池反而受保護（刻意不級聯）。
- 根因：級聯設計照「資料關聯（clientId 外鍵）」走，沒照「資產價值/團隊歸屬」走。捐入帳號在語意上已是團隊池資產（跟爆文一樣），卻沒享同款「刪成員不刪」保護。
- 下次：設計級聯刪除時先問「被連帶刪的東西，哪些其實是團隊/共享資產？」——共享資產一律解綁不刪。刪除的爆炸半徑要按價值畫，不按外鍵畫。
- 對應 feedback：feedback_defend_at_convergence_point 的反面教材（去重/歸屬的咽喉沒守住價值邊界）；surface_technical_debt（已主動點出待修）。
