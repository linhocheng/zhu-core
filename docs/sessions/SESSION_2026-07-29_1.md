## 教訓
### L1:監看條件裡「目標不存在」≠「目標完成」——自製的模稜兩可信號
- 現象:Monitor 用「builds list 沒有 WORKING」當建置完成;gcloud 憑證壞掉後 submit 根本沒提交,列表本來就沒有 WORKING → 假 SUCCESS 通知,兩輪「部署」實為空氣
- 根因:①管子吃退出碼(踩過的雷再踩:`submit | tail` exit=tail 的)②監看分支把「無目標」與「終態」合流 ③收案信號用「設定面」(我以為提交了)不用「產物面」(build ID/image digest)
- 下次:背景提交一律先拿到**具體 ID** 再掛監看;監看鎖 ID 的顯式狀態;部署收案=build digest 對 serving revision digest;凡 `| tail/grep` 的指令不得作為成敗判據
- 對應 feedback:pipe_eats_exit_code(二進宮)、ambiguous_signal_not_proof(新形態:自製監看濾網也會產生模稜兩可信號)

### L2:「LLM 呼叫無狀態」是要驗證的假設,不是公理
- 現象:prompt 六層全排除仍洩漏客戶資料;真兇=bridge claude CLI 的 auto-memory 跨租戶注入
- 根因:CLI 型引擎(相對直連 API)自帶 per-cwd 記憶與 session;無人在部署第一天把它關掉,因為沒人意識到它開著
- 下次:任何 headless CLI 服務上線清單加一條「狀態性盤點」(auto-memory/session/CLAUDE.md 吃什麼);洩漏排查把「引擎層」列為與 prompt 平行的審計面
- 對應 feedback:bridge_cli_auto_memory_contamination(本場新刻)、glue_layer_errors_lie
