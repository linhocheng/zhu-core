## 教訓

### L1：災難才跑的路徑，出貨必須帶陽性對照 harness
**現象**：昨天出貨的熔斷跳句路徑有「未 initialize 就 flush 必炸」沉睡 bug；今天的觀測又抓到空跑 0 bytes 誤計分。兩條都在「熔斷從沒真的開過」的陰影下安全潛伏。
**根因**：主路徑天天跑所以壞了會知道；熔斷/備援只在災難時跑，壞了沒人知道直到災難當天（比較報告 §5.3 自己寫的話，隔天應驗在自己身上）。
**下次**：熔斷器/fallback/災難恢復類 code，harness 與本體同一個 commit 出貨；mock 要仿真實契約（MockEmitter 學真 AudioEmitter 的先 initialize 才能 flush），寬鬆 mock 抓不到契約 bug。
**對應 feedback**：feedback_ambiguous_signal_not_proof（「沒失敗」在沒跑過的路徑上是零資訊）

### L2：收攤還原要還原到「記錄的前置狀態」，不是「假設的預設值」
**現象**：測前沒抄下 voicePower 現狀就開測；用戶撥號的合法喚醒把傘拉到 min=1；收攤直寫 on:false 只還原旗標沒降實例——旗標關/實例燒的真相分裂，自己造的。
**根因**：SOP 寫「還原 standby/off」是假設測前就是這個狀態；喚醒流程是前端開頁就打的，測試期間系統狀態會被合法路徑改變。
**下次**：測前第一動作抄現狀（旗標全文）；收攤對照現狀還原＋逐服務降實例＋計費面複核三件一組。已寫進 canary SOP 正文。
**對應 feedback**：feedback_cost_verify_billing_meter_not_config

### L3：LLM 動態注入的位置決定快取存亡——system 尾端是最貴的注入點
**現象**：v20m 每次「想起/知識注入」append 到 system prompt，Anthropic 前綴快取順序 tools→system→messages，破 system＝整段對話歷史陪葬；越長的通話破一次越貴。
**根因**：把「動態上下文」和「行為指令」都當成 instructions 塞 system——注入內容其實是素材不是指令，放 messages 尾端（developer role）快取全保；狀態型指引（走步）搭 tool result 天然免費。
**下次**：任何 LLM pipeline 的動態注入先問「這會不會動到快取前綴」；role=system 的 chat 訊息會被 provider format 抬升回 system 參數＝照樣破，要用 developer/user role。細節在新 memory reference_anthropic_prompt_cache_injection。
**對應 feedback**：新增 reference（可移植架構規律）
