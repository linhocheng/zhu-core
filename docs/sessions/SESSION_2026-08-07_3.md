## delta
**進場前以為**：比較報告的 Tier 1「真優點」＝可直接移植的工單，六項排程做完就是 V20M。
**現在理解**：優點清單還要過**第四關——逐項讀自己的 code，看自己是否已用別的方式解掉**。六項過完只剩兩項：②早解了（prompt 整通穩定天然命中快取）、③違反自家設計、⑥會弄壞現有行為、①是重工。而且方向是反的：漫漫三處「借鏡 ailivex」，我們才是上游。
**移動原因**：每次動手前讀目標檔本體（minimax_tts/interrupt_gate/firestore_loader），三次都在動手前發現「這項不該做」。如果照清單直接寫，⑥會讓正常音量插話失靈、③會讓所有角色講話像漫漫。
**違背了哪條 feedback**：無違背，但③是在懸崖邊被 feedback_global_prompt_must_not_encode_personality 拉回來的——我已經在寫注入 prompt 的措辭了。

## 教訓

### L1：別人系統的優點清單，落地前要過第四關——自己的 code 可能已解
**現象**：比較報告 Tier 1 篩過三關（脈絡可拔/真問題/對產品對）的六項「真優點」，逐項讀自家 code 後只剩兩項活著。
**根因**：報告比的是「兩邊都有沒有」，沒比「沒有的那邊是否用別的機制解了同一問題」——prompt cache 就是：ailiveX 沒有切點設計，但 prompt 整通建一次天然全命中，切點是替每輪重建的架構解的。
**下次**：優點移植工單開工前，每項先問「我的架構裡這個問題存在嗎」，貼目標檔實讀證據才進工單。
**對應 feedback**：feedback_diagnosis_verify_before_write（延伸：診斷對了，處方還要對體質）

### L2：canary 測試不碰全域電源 mode——reconciliation 會拉整傘
**現象**：forceready 圖方便設 `voicePower.mode='on'`，電源傘 reconciliation 把 v19/v20/v21 全拉 min=1，三顆常駐偷燒；旗標還原後實例不會自動降。
**根因**：mode 是全域意圖，改它＝叫系統把傘下所有版本對齊到 min=1；還原旗標只改意圖不改事實（設定面≠計費面）。
**下次**：傘外 canary 只精準 `gcloud run services update <svc> --min-instances=1`，不碰 config/voicePower.mode；收尾逐服務查 minScale annotation 歸零才收案。
**對應 feedback**：feedback_cost_verify_billing_meter_not_config

### L3：喚醒流程會頂 onSince——傘外服務永遠「開機中」
**現象**：Adam 撥號報「引擎無法啟動」。v20m boot 10:12，但每按一次撥號、喚醒流程把 onSince 刷成現在 → bootAt > onSince 永遠 false → 越按越糟。
**根因**：readiness 判準（bootAt > onSince）假設「喚醒的服務就是會被重啟的服務」；傘外 canary 被喚醒流程刷 onSince 卻不會被重啟，判準的前提斷了。
**下次**：傘外 canary 供電後把 onSince 釘在 bootAt 之前＋mode 保持不觸發喚醒；或（正解）測試期把 canary 加進 CANARY_VOICE_VERSIONS 再拔。
**對應 feedback**：feedback_interface_blood_vessel_check（誰讀 onSince/何時刷/傘外沒人重啟）
