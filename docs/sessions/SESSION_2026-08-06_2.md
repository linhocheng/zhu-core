## 教訓

### L1：過期的記憶不會腐爛成沉默，會腐爛成有害指令

**現象**：`feedback_killall_vs_pkill` 給的標準指令是 `killall -9 node + nohup`，但 bridge 早由 systemd 接管，照做起兩個 process（MOLOWE 產 4 篇而非 2 篇的事故根因）。`reference_cloudrun_background_task_sop` 檔頭疊兩層「已退役」補丁，正文照舊完整教 `--min-instances=1`。
**根因**：記憶的「過期」被想像成「內容變舊、參考價值下降」。實際上**給現成可貼指令的記憶，過期後是負值不是零值**——它比沒有記憶更糟，因為它帶著天條的權威。而檔頭加補丁擋不住掃讀，掃讀的人看到程式碼區塊就複製。
**下次**：推翻舊解法時**動正文**，不是在檔頭加補丁。給指令的記憶要寫「判準」不只寫「指令」（本檔 cloudrun SOP 重寫後開頭就是「先分類：這台閒著時有沒有人下一秒需要它」）。
**對應 feedback**：新開一條「記憶的過期分兩級：知識過期是零值，指令過期是負值」。

### L2：掃描工具本身是需要被驗證的對象

**現象**：`ugrep --hidden -rl ... → 0 命中`，我報告「乾淨」。實際上這台機器沒有 `ugrep` 這個指令名（`grep` 才是 ugrep），指令根本沒執行，我把 command-not-found 的空輸出讀成掃描結果。更早一步：ugrep 預設跳過隱藏檔，所以我第一輪「憑證洩漏只有一件事」的結論建立在**完全沒掃 .env** 的掃描上。
**根因**：把工具當透明的。驗證別人的東西時很警覺，但**執行驗證的那個工具自己沒被驗證**。「0 命中」和「指令沒跑」在輸出上長得一模一樣——這就是零資訊信號的最純形式。
**下次**：任何掃描器在信它的「0 命中」之前，**先拿一個已知會命中的樣本測它**。這次是靠 `jianbin-v2-keys` 在我記憶裡才抓到，那是運氣不是方法。
**對應 feedback**：`feedback_ambiguous_signal_not_proof` 的工具版，`skill_filter_unit_matches_error_shape` 的上游。

### L3：記憶庫不是 secret store

**現象**：GEMINI_API_KEY 完整明文寫在 `reference_zhu_migrate_plist_keys.md` 裡 91 天。而記憶庫 (a) 每 6 小時被 migrate 讀去入庫 Firestore (b) 有第二份實體副本在 zhu-core/memory (c) **那份在 git，且 repo 是 PUBLIC**。一份明文散佈到三個地方，最後被 Google 的洩漏掃描器抓到並自動停用。
**根因**：寫那條記憶時的心智模型是「記下來免得忘記」，沒有問「這份記憶會流到哪裡」。記憶檔看起來像本機筆記，實際上是**會自動扇出的發佈管道**。
**下次**：記憶記「key 叫什麼、去哪拿、沒有會怎樣」，永遠不記值。新增記憶時問一次血管三問的變體：**這條會流到哪裡？誰會讀到？**
**對應 feedback**：`feedback_interface_blood_vessel_check` 的反向用法（平常問「血管接通了嗎」，這裡要問「血管通到不該通的地方了嗎」）。

### L4：驗證流程走完了，不代表驗證發生了

**現象**：換完 key 我跑 migrate、看到 `[done] 130 chunks upserted`、`fail=0`、`403=0`，宣告修好。實際上 log 才 17 行，328 個檔案跑了 11 個。第二次我用 `pgrep` 判斷進程結束，在父子進程交接的瞬間讀到 0，又宣告完成。
**根因**：這是「模稜兩可信號」家族的第四張臉——前三張是**沒驗 / 標了沒驗 / 驗了但信號零資訊**，這張是**驗證正在進行中，我把中途快照當終局**。最隱蔽，因為所有指標都是綠的，只是還沒跑到會紅的地方。
**下次**：進度型驗證要先問「**完成的絕對條件是什麼**」（本例：`launchd state != running` ＋ `last exit code = 0`），不能用「目前為止沒有失敗」代替。零失敗在 11/328 的情況下與成功不相容。
**對應 feedback**：`feedback_ambiguous_signal_not_proof` 加第四張臉。
