## delta
進場前以為：debug 時直撈 DB 是最快的真相——查到什麼回報什麼。
現在理解：**原始層查詢的結果不是產品真相**。業務層過濾（archived/screened/scope）才決定用戶會看到什麼；繞過它查到的「事實」拿去回報 UI 行為＝說謊而不自知。Alex 案我報「四位角色都能選」，實際 UI 三位——查詢是對的、回報對象錯了層。
移動原因：Adam 拿我的錯誤回報來問「是不是 bug」——我的回報汙染變成了他的假警報，查完才發現 bug 是我的話不是系統。
違背了哪條 feedback：diagnosis_verify_before_write 的變體——寫「會看到什麼」之前，要走跟 UI 同一條讀路徑。

## 心法狀態
- 「宣告修好前先指出鑑別信號」兩次正面實戰：阿瑞/開賭場（只存在補充資料）、「所選角色」新錯誤文案（舊代碼無此路徑）——兩次都先寫下 X/Y 才驗
- 「假中台審計」用在資料管道：補充成功訊息 ≠ 資料到達消費端，逐段追到四條生成線全接通
- 「防禦釘在收斂點」：brief-context 一個咽喉守四條線（worker 鏡像是獨立部署的必要之惡，已互註）

## 教訓
### L1：debug 直撈 DB 的結果不能當 UI 行為回報
- 現象：raw Firestore query 列出四位角色（含 archived 的 Alex），回報 Adam「四個聲音都能選」；實際 UI 走 getCharacters() 過濾後只有三位，Adam 誤以為系統有 bug
- 根因：查詢層級錯位——原始層看得到的，業務層不一定放行；回報對象是「UI 會顯示什麼」時必須走同一條讀路徑
- 下次：回報用戶可見行為前，打產品 API（或聲明「這是原始層資料，UI 可能過濾」）；debug script 輸出自帶層級標籤
- 對應 feedback：diagnosis_verify_before_write／memory_can_lie 家族新成員
