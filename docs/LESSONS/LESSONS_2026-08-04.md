# LESSONS 2026-08-04 · DreamF 管線 V2→V3 一日兩翻——母資產前移＋圖像全走 GPT 底片感，三 e2e 交片

### L1：LLM 產出的 prompt 疊拼裝模板＝兩個生成器互踩——拼裝層要防「語意重複」不只防「格式錯誤」
- 現象：Vertex SAFETY 三波假案，真兇全是拼裝層把否定條款（no text/no people）疊在 LLM 已寫好的否定條款上，「否定連跑」形狀觸發 prompt-level filter
- 根因：模板寫死尾綴的年代，prompt 是人寫的不會重複；promptEn 改由 LLM 生成後，模板不知道 base 已含什麼
- 下次：任何「LLM 內容＋程式模板」拼裝點，先問「兩邊會不會說同一句話」；去重防線釘在拼裝咽喉（appendUniqueClauses），極端解＝原文直出（風格幀鐵律）
- 對應 feedback：feedback_defend_at_convergence_point 的 prompt 版

### L2：同步 request 裡的生成呼叫要用「單次呼叫的 P99 × 張數」估上限，不是「平均能跑完」
- 現象：面談收卷同步生兩張 gpt-image（60-90s/張）→ 超過 client timeout → 斷線 CPU 掐死 → 資料半熟＋錢已燒
- 根因：Nano Banana 時代單張 10-20s 僥倖能活，換引擎沒重估時間預算——容量常數會過期（feedback_capacity_constants_expire 的延遲版）
- 下次：route 裡任何生成呼叫，換引擎/換畫質時重算「最壞情況總時長 vs timeout」；超過 1/3 就搬 job
- 對應天條：Cloud Run 無 fire-and-forget——這次是它的「同步偽裝」變體：不是忘了等，是等不起

### L1：ExitPlanMode 的 approval 文字是工具通用文案,不等於使用者當下的真實意圖
- 現象：ExitPlanMode 回傳「You can now start coding」，但 Adam 同一則訊息明確寫「還先沒有要施工」
- 根因：plan mode 的核准機制是 UI 層的按鈕/流程，跟聊天視窗裡的文字指令是兩個訊號來源，工具的制式文案可能跟使用者當下最新表態不同步
- 下次：任何工具回傳的「可以開始做」，都要跟使用者最近一則訊息的明確文字對照，文字優先於工具制式文案
- 對應天條：feedback_clarify_before_execute（沒說動手就不動手）

### L1：不可變資源才配長快取——會被覆寫的路徑要嘛短快取要嘛版本化，兩者擇一必須顯式選
- 現象：資產「這張重生」成功但客戶永遠看到舊圖，零錯誤 log，一年內不會自癒
- 根因：`uploadBuffer` 對所有路徑一律掛 `max-age=31536000`——那是為「幀圖生成一次就不動」設計的常數；V2 加了重生功能後同一路徑變成可變資源，常數沒跟著改
- 下次：任何 `uploadBuffer`/CDN 寫入點，先問「這路徑會不會被同名覆寫」；會＝must-revalidate 或版本化。已上傳的舊物件別忘 `gsutil setmeta`（新策略不追溯）
- 對應 feedback：feedback_capacity_constants_expire ＋ feedback_defend_at_convergence_point
