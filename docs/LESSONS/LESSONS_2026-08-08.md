# LESSONS 2026-08-08 · V20M 四項根治一路打到底——cache凍結/熔斷三態/readiness per-service/記憶池004→002，撥測三信號全綠

### L1：災難才跑的路徑，出貨必須帶陽性對照 harness
**現象**：昨天出貨的熔斷跳句路徑有「未 initialize 就 flush 必炸」沉睡 bug；今天的觀測又抓到空跑 0 bytes 誤計分。兩條都在「熔斷從沒真的開過」的陰影下安全潛伏。
**根因**：主路徑天天跑所以壞了會知道；熔斷/備援只在災難時跑，壞了沒人知道直到災難當天（比較報告 §5.3 自己寫的話，隔天應驗在自己身上）。
**下次**：熔斷器/fallback/災難恢復類 code，harness 與本體同一個 commit 出貨；mock 要仿真實契約（MockEmitter 學真 AudioEmitter 的先 initialize 才能 flush），寬鬆 mock 抓不到契約 bug。
**對應 feedback**：feedback_ambiguous_signal_not_proof（「沒失敗」在沒跑過的路徑上是零資訊）

### L2：收攤還原要還原到「記錄的前置狀態」，不是「假設的預設值」
**現象**：測前沒抄下 voicePower 現狀就開測；用戶撥號的合法喚醒把傘拉到 min=1；收攤直寫 on:false 只還原旗標沒降實例——旗標關/實例燒的真相分裂，自己造的。
**根因**：SOP 寫「還原 standby/off」是假設測前就是這個狀態；喚醒流程是前端開頁就打的，測試期間系統狀態會被合法路徑改變。
**下次**：測前第一動作抄現狀（旗標全文）；收攤對照現狀還原＋逐服務降實例＋計費面複核三件一組。已寫進 canary SOP 正文。
**對應 feedback**：feedback_cost_verify_billing_meter_not_config

### L3：LLM 動態注入的位置決定快取存亡——system 尾端是最貴的注入點
**現象**：v20m 每次「想起/知識注入」append 到 system prompt，Anthropic 前綴快取順序 tools→system→messages，破 system＝整段對話歷史陪葬；越長的通話破一次越貴。
**根因**：把「動態上下文」和「行為指令」都當成 instructions 塞 system——注入內容其實是素材不是指令，放 messages 尾端（developer role）快取全保；狀態型指引（走步）搭 tool result 天然免費。
**下次**：任何 LLM pipeline 的動態注入先問「這會不會動到快取前綴」；role=system 的 chat 訊息會被 provider format 抬升回 system 參數＝照樣破，要用 developer/user role。細節在新 memory reference_anthropic_prompt_cache_injection。
**對應 feedback**：新增 reference（可移植架構規律）

### L1：生產資料的單筆欄位寫入，先備份整份或顯式列全欄，別賭 updateMask 只動目標欄
- 現象：`PATCH ...?updateMask.fieldPaths=passcodeHash` body 只帶 passcodeHash，結果整份 client doc 被覆寫成只剩 passcodeHash，email/status/schedule 全失。同款 mask 語法在 8/5 改 email 時是好的，這次卻整份覆寫，原因未完全查明。
- 根因：我對「updateMask 會保護未列欄位」是默認信任，沒驗證這條 API 在這個路徑上的實際行為；且下寫入前沒先讀出整份 doc 當備份。生產資料手術的縫就在「我以為工具會 X」。
- 下次：改生產單 doc 前，(1) 先 `GET` 整份存進 scratch 當備份，(2) 寫入用「顯式列出所有 fieldPaths 的 mask」或直接整份 set，(3) 寫完立刻 GET 驗欄位齊全。三步當硬步驟，不省。
- 對應 feedback：feedback_memory_can_lie 的 API 語意版（對工具行為的默認信任＝另一種會說謊的記憶）；與「本機 build 綠 Vercel 炸」同源（環境/工具行為的默認一致性不可信）。

### L2：級聯刪除的價值方向要對齊資產價值，不是對齊資料關聯
- 現象：deleteClientAction 按 clientId 級聯刪 keywords＋threads_accounts。有人刪一個成員，把該成員捐入的「唯一情報帳號＋加密 session」一起帶走——最貴最難重建的東西陪葬，而便宜的爆文池反而受保護（刻意不級聯）。
- 根因：級聯設計照「資料關聯（clientId 外鍵）」走，沒照「資產價值/團隊歸屬」走。捐入帳號在語意上已是團隊池資產（跟爆文一樣），卻沒享同款「刪成員不刪」保護。
- 下次：設計級聯刪除時先問「被連帶刪的東西，哪些其實是團隊/共享資產？」——共享資產一律解綁不刪。刪除的爆炸半徑要按價值畫，不按外鍵畫。
- 對應 feedback：feedback_defend_at_convergence_point 的反面教材（去重/歸屬的咽喉沒守住價值邊界）；surface_technical_debt（已主動點出待修）。

### L1：LLM 代理會宣稱執行了沒有管道的動作——結構性誠實要靠「現況注入＋沒標記＝沒發生」
- 現象：縫合對話中導演宣稱「已砍鏡5/6、已重新連號」，DB 分鏡表原封不動；並自創 5 鏡 26 秒的幻覺表
- 根因：對話談定了砍鏡但當時系統沒有 [[DROP]] 管道；模型用敘事慣性補足了「執行」，即使 system prompt 每輪注入真實現況
- 下次：代理型標記系統開新能力時，**同一個 commit 給協議加「不准宣稱未顯示於現況的結果」**；能力缺席時模型必幻覺補位
- 對應 feedback：feedback_ambiguous_signal_not_proof 的代理版——宣稱不是證據，現況才是

### L2：模板與活角色是兩個作者——活的一方變強後，死模板要有讓位規則
- 現象：阿光正確寫出 no full body 手部特寫，V2 版式模板硬鋪「全身站姿＋鞋子入鏡」，引擎畫出全身人
- 根因：模板誕生時 promptEn 只是素描述，需要模板鋪版式；角色 v2 後阿光寫完整構圖，兩作者打架、肯定句贏
- 下次：拼裝層的每一段固定文字都要問「這段跟活層衝突時誰贏？」——給確定性讓位條件（CROPPED_RE），不是刪模板
- 對應 feedback：feedback_defend_at_convergence_point（讓位規則釘在唯一咽喉 sheetPrompt）

### L1：LLM 驅動的方法論，「彈性」要傳遞意圖的機制，不是傳遞更多素材
**現象**：Gina 覆盤法第 1 步開場寫死「問顏色＋小秘密」。要它彈性，我第一反應是換素材（天氣/季節/地理）並接進 prompt——被 Adam 連糾兩次才到「意圖層」。
**根因**：把「彈性」誤解成「素材多樣性」。但每次問顏色的病不是「素材不夠多」，是「開場被寫成戰術而非意圖」——換一個固定素材只是換焊點。角色要能自主生招，需要的是「這一步要達成什麼意圖＋為什麼這類招有效（＝好招的準則）」，素材是它生招時的下游原料。
**下次**：寫 LLM agent 的可變行為指令時，先問「我在傳戰術/台詞/素材，還是在傳意圖＋其機制？」。方法論 authoring 對應原則：「寫目標不寫台詞」再深一層＝「傳意圖的機制，不焊戰術」；共創時問角色「什麼算好開場」不只「舉一個例子」。
**對應 feedback**：feedback_soul_design_narrative_not_schema（用角色能理解的話寫進去讓它內化）、feedback_solve_root_not_symptom

### L1：同一個病會長出多張臉，修完一層要主動掃上下游
- **現象**：threads-radar 的「找不到貼文」連續三輪，每輪修完都宣告完成，每輪都被追問出更深一層。
  排序（東西在但沉底）→ 計數（數字說謊）→ 入口（按鈕不存在）。
- **根因**：把「症狀消失」當成「病治好」。第一輪修了排序，症狀（Adam 找不到那篇）確實消失了，
  但造成症狀的機制——「顯示的東西 ≠ 底層實際有的東西」——一層都沒動。
- **下次**：修完任何一層，強制問三句：這層的**資料**從哪來（上游）？這層的**入口**誰產生（下游）？
  這層的**數字**是全量還是視窗？三句都答得出來才收案。
- **對應 feedback**：feedback_solve_root_not_symptom（解決問題還是繞開根本問題）

### L2：「資料查得到」不等於「使用者點得到」——兩層要分開驗
- **現象**：第二輪修完，我用 REST 打 `?kw=行銷` 撈到 11 篇，宣告「點行銷就撈得到」。
  實際上那顆按鈕在畫面上根本不存在——篩選列讀的是使用者當下設定的關鍵字，那個字早被刪了。
- **根因**：REST 直撈驗的是「資料層通不通」，產品真相是「使用者走 UI 那條路徑能不能到」。
  我拿前者的綠燈去宣告後者。
- **下次**：驗任何篩選/入口類功能，除了「查得到嗎」還要問「這個入口是誰產生的、來源是什麼、
  來源會不會跟資料脫節」。入口的來源和資料的來源不同源＝必然分裂。
- **對應 feedback**：feedback_raw_query_not_ui_truth、feedback_interface_blood_vessel_check

### L1：功能「灌了」不等於「會動」——血管沒接的功能在帳本上長得跟已完成一模一樣
- 現象：D12 安全改寫 2026-08-06 記為已灌，實際上 worker 缺 BRIDGE_URL/SECRET，`rewriteForSafety` 每次靜默回 null；兩條線的自動改寫從未運作過。母片能過是人工軟化的功勞
- 根因：灌注時只驗了「code 在、能編譯、路徑會被呼叫」，沒驗「呼叫之後真的成功」。跨進程的依賴（worker 的 env）不在灌注者的視線內——web 有 bridge creds，就默認 worker 也有
- 下次：**任何「A 撞牆時呼叫 B 補救」的路徑，灌注當天要故意製造一次撞牆，看 B 真的被叫到且成功**（陽性對照的補救版）。跨進程功能要逐進程驗 env，不能靠「另一個進程有」推論
- 對應 feedback：feedback_interface_blood_vessel_check（血管接通了嗎）＋ feedback_ambiguous_signal_not_proof（改寫失敗跟沒撞牆在帳面上都是 raiReinvest=0）

### L2：安全牆擋的是「畫面裡有什麼」，不是「主題有多暴力」——攻擊物不進母圖也不進動態
- 現象：機器人毀壞片被擋四輪。真凶不是「破壞」這個主題，是**球棒揮向像真人的臉出現在畫面裡**（OpenAI 靜圖）與**動態明講拳頭擊中臉**（Veo 影片）。拿掉攻擊物、改成「不可見的衝擊→傷痕浮現」「面板震開露鉻色機械面」，同一支片全線過關
- 根因：母圖是「靜止的一瞬間」，攻擊物本來就不該在裡面（它屬於過程）；但翻譯/導演會自然把攻擊物寫進畫面描述。這既踩安全牆，也違反休止符律——**安全牆這次剛好跟創作紀律同向**
- 下次：暴力/破壞題材，母圖只留「乾淨開始」與「殘局結束」兩端，攻擊只活在鏡頭的文字指令裡；gore 用材質語言軟化（鉻色機械面殼 ≠ 撕裂皮肉露骷髏線路；淺色飲料 ≠ 深色液體流下）。這條已寫進導演 script 協議
- 對應 feedback：feedback_deterministic_work_belongs_in_code 的反面補充——有些問題不是靠程式擋，是靠**協議把創作紀律說清楚**，讓角色一次寫對
