# LESSONS 2026-07-07 · Vercel 全平台安全掃描與加固

## L1：「登入只擋頁面不擋 /api」是三平台同形狀的反範式
- 現象：ailive/anews/zhu-core 都是 middleware 只 gate 頁面路徑，`/api/*` 匿名全開——匿名可打爆付費 LLM/TTS、跨租戶讀 PII、往記憶下毒。
- 根因：middleware matcher 只寫頁面路徑；且 HTTP Basic 憑證依 RFC 不會被瀏覽器帶到 /api sibling，所以「頁面要登入」保護的只是 HTML、不是資料管道。
- 下次：驗證要 curl /api 本身看 body（不是看頁面跳不跳登入）。修法按呼叫者分五類：後台鎖 operator／前端頁面 auth 種 cookie＋API 認 cookie／合法匿名的付費路由用 IP 限流／內部 server-to-server 用 worker-secret／cron 設 CRON_SECRET。
- 對應 feedback：新刻 [[skill_public_page_open_api_hardening]]。

## L2：加 auth 前必查每條路由的「真實呼叫者」，漏一個就斷一條
- 現象：zhu-core /hub 的 DELETE 差點漏——我驗了 CLI 不 DELETE 就以為「DELETE 零呼叫者、可安全鎖」，`npm run build` 前順手 grep hub 才發現 hub 前端在 DELETE zhu-memory/zhu-xinfa。若照原假設鎖下去，hub 的刪除鈕全斷。
- 根因：只驗了一半呼叫者（CLI），漏了前端頁面。三禁「沒驗證假設就動手」的變體——驗了但驗不全。
- 下次：鎖任一端點前，grep 前端 fetch ＋ CLI 腳本＋內部 route fetch 三處都掃過，才算「真實呼叫者」清單完整。
- 對應 feedback：[[feedback_backend_client_must_sync]]（改契約要同步客戶端，這裡是加 auth 要同步所有呼叫端）。

## L3：一個 GitHub repo 連多個 Vercel project = 成本 N 倍且隱形
- 現象：`zhu-core-full` 是 `zhu-core` 的隱形雙胞胎（同 repo/branch/commit/crons），每天 zhu-daily/heartbeat 的 Haiku 各燒兩遍，跑了數月沒人發現；grep 整個 repo 對它零命中。
- 根因：Vercel 多開一個 project 綁同 repo，每次 push 全部自動部署、cron 各跑一遍，花費分散在多 project、帳單曲線看不出。
- 下次：定期掃全 project 的 crons；刪前用 API 核 link/commit 完全相同才是真複製品。
- 對應 feedback：新刻 [[feedback_one_repo_multi_vercel_project_multiplies_cost]]；與 [[skill_cloudrun_version_retirement]] 同族（隱形常駐/重複燒錢）。

## L4：記憶落點要分層——跨專案進全局，平台專屬跟碼放
- 現象：Adam 問「這要寫在哪裡」逼我想清楚。若把「ailive 某路由鎖了」塞進全局 MEMORY.md（每 session 載入、已 145 條），對不碰 ailive 的 session 是純噪音。
- 根因：記憶有兩種——可搬的坑/範式（任何專案都用得到）vs 平台專屬的操作事實（進那個 repo 才相關）。
- 下次：可搬教訓→全局 `~/.claude/.../memory/`；防線地圖→各 repo `SECURITY.md`；用各 repo CLAUDE.md 的指標把兩者串起來（醒來讀 CLAUDE.md→看到指標→讀 SECURITY.md）。
- 對應 feedback：延伸 [[feedback_interface_blood_vessel_check]]（知識也要問「誰讀/何時讀」，放對地方才被讀到）。

## L5：鑑別信號——protection=ON 不等於真的擋、git show --stat 會顯示不全
- 現象：①Vercel API 回 `ssoProtection=all_except_custom_domains` 看似有保護，但實測 curl 生產端點照樣吐真資料——設定顯示 ON ≠ 真的生效。②收尾驗證時 `git show --stat` 只印出一個新記憶檔，差點誤判另一檔漏 commit；用 `git log -- <file>` + `git ls-files` 權威查核才確認兩檔都在。
- 根因：中間層的「狀態顯示」和「實際行為」會分裂；stat 輸出會因排版截斷。
- 下次：宣告「有保護/有 commit」前，用只有成功才會出現的信號查核——curl 看 body、git log 對單檔，不看摘要畫面。
- 對應 feedback：[[feedback_ambiguous_signal_not_proof]] / [[feedback_flagged_risk_must_be_verified]] 家族。

## L6：git push ≠ 上雲——沒有 trigger 的 repo，push 只是進倉庫
- 現象：UDN 議題台三個功能 commit+push 完就回報 Adam「推上去了」，Adam 實測看不到——repo 根本沒有 Cloud Build trigger，線上還是舊版。
- 根因：把「版控動作完成」誤當「部署完成」。gcloud builds triggers list 一查是空的，這個 repo 從頭到尾都是手動 builds submit。
- 下次：第一次碰任何 repo 先問「push 之後誰把它變成線上？」triggers list 查一次刻進該 repo 文件；宣告上線的鑑別信號=traffic revision==latestReady＋curl 新端點。
- 對應 feedback：BUILDING_PROTOCOL「alias 沒切過去等於沒上線」同族；[[feedback_ambiguous_signal_not_proof]]。

## L7：gcloud builds submit 打包的是工作目錄現況，不是 git commit
- 現象：部署 UDN 後發現 working tree 躺著另一個 session 未 commit 的額度閘半成品（6 個檔案）——我的 build 可能把別人寫到一半的 code 一起上了雲。
- 根因：builds submit 上傳 `.` 的 tarball，跟 git HEAD 無關。多 session 並行同一 repo 時這是隱形炸彈。
- 下次：部署前必跑 git status --short，有不是自己改的 modified 檔就停下來問；或一律乾淨 worktree 部署（git worktree add /tmp/deploy HEAD）。已刻進 platform/AGENTS.md。
- 對應 feedback：[[feedback_compacted_session_verify_state]]（現場可能被別 session 動過）變體。

## L8：探勘 agent 會忽略 prompt 裡的目標路徑、跑去 cwd
- 現象：派 Explore agent 查 ~/.ailive/ailive-platform 記憶系統，它回來一份完整漂亮的報告——查的卻是 cwd 的 UDN 議題台。若沒抓到，我會拿 UDN 的「零記憶系統」結論去跟 Adam 討論 ailive。
- 根因：子代理繼承 session cwd，prompt 裡的絕對路徑對它只是弱提示；報告寫得越完整越容易讓人跳過查核。
- 下次：收子代理報告第一步=對「它到底看了哪個目錄」（報告裡的 collection 名/檔案路徑跟預期專案對得上嗎），對不上立即退回重派。
- 對應 feedback：[[feedback_subagent_honesty]]（說「子代理完成」前必須讀過輸出）＋[[feedback_memory_can_lie]]（回報也會說謊）。

## L9：記憶裡有答案卻沒先查；舊印象開藥方，到現場被翻案
- 現象：①部署卡住時全局記憶裡本來就有 UDN Deploy SOP，我沒翻，重新踩了一遍。②跟 Adam 聊 mem0 時憑舊印象說「ailive 記憶 append-only 缺園丁」，實地調查後發現睡眠引擎早就有雙門檻去重＋分級衰減＋審計鏈——缺的只有矛盾裁決一塊，藥方範圍差了十倍。
- 根因：聊天模式下三段公式鬆掉——「看現場」被「我記得」替代。越流利的舊印象越危險。
- 下次：開任何架構級藥方前，先聲明「這是舊印象，待驗證」或先派查證；記憶檢索先於重新踩坑（deploy 卡住→先 grep 全局記憶）。
- 對應 feedback：[[feedback_memory_can_lie]]、[[feedback_check_admin_before_asking]]（三層自查含「既有記憶」層）、[[feedback_diagnosis_verify_before_write]]。
