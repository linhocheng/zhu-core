# LESSONS 2026-07-02 · ailivex podcast 生產線（超時根治 + 語感 + 文字過濾器）

## L1：模稜兩可的信號不能當成功證據（驗證失守第三張臉）
- 現象：CPU throttle 修法（保持 request open）部署後，測試回 `HeadersTimeoutError`，我當場解讀成「這正是修法生效的證明」。查 Firestore 才發現兩個 2500 字任務全卡 running、container 半途被換，修法無效。差一步就跟 Adam 說「修好了」。
- 根因：timeout/沉默/連線錯誤類信號跟「成功」「卡死」**兩邊都相容**＝零資訊；剛部署完自己的修法，會本能往「生效了」解讀（展示衝動的變體）。
- 下次：宣告修好前先寫下「修好了會看到 X、沒修好會看到 Y」，X 必須是失敗時不可能出現的（DB 目標狀態、log 完成行、產出檔案）。timeout 類信號一律不算數。
- 對應 feedback：新刻 `feedback_ambiguous_signal_not_proof`；家族＝`feedback_sandtable_not_validation`（沒驗）→ `feedback_flagged_risk_must_be_verified`（標了沒驗）→ 本條（驗了但信號零資訊）。

## L2：Cloud Run「client 斷線＝request 結束」——保持 request open 救不了 fire-and-forget
- 現象：worker 改成「做完才回應」想閃 CPU throttle，Vercel 端 10s AbortSignal 斷線後 Cloud Run 照樣 throttle + `min-instances=0` 把跑到 14 分鐘的 container 回收。
- 根因：Cloud Run request-based billing 只看「有沒有 active request」；client 斷線 request 就結束了，server 端 Node 還在跑也沒用。
- 下次：Cloud Run 後台長任務三件套 deploy flag：`--no-cpu-throttling` + `--min-instances=1` + 先回 202 再 `setImmediate`。診斷信號：短任務成功長任務卡 running、log 中間插新的 `listening on :8080`。
- 對應 feedback：新刻 `reference_cloudrun_background_task_sop`。

## L3：Node ESM 相對 import 必帶 .js——tsc 綠 ≠ runtime 通
- 現象：worker 加第一個相對 import（`./text-filter`），tsc 全綠、Cloud Build FAILURE：container 起不來，revision log `ERR_MODULE_NOT_FOUND`。
- 根因：tsconfig `moduleResolution: bundler` 編譯期放行無副檔名，Node ESM runtime 要求完整 `.js`。
- 下次：Node ESM 專案相對 import 反射帶 `.js`；專案第一次加相對 import 時 build 完本機 `node dist/index.js` boot 一次再推。
- 對應 feedback：新刻 `reference_node_esm_import_js_extension`；同族 `reference_dynamic_import_not_bundle_fix`（編譯綠≠執行通）。

## L4：過濾器的攔截單位要對齊錯誤的真實形狀（句型不是單字）
- 現象：Adam 要擋「鬆了一點」類 AI 詞，直覺是單字黑名單——但「螺絲鬆了」是人話會被誤殺。升級成句型 pattern（模糊主語＋體感動詞）後，「好像有什麼鬆了」抓、「那個『我』自然就鬆了」（禪語，主語具體）放行，同一個字一抓一放。
- 根因：AI 味的最小完整形狀是句型結構不是字。
- 下次：建黑名單前先收 5-10 壞例＋5-10 易誤殺好例，找「壞例共有、好例沒有」的結構特徵；配套＝LLM 只改踩雷句（保護已做對的角色感）＋過濾釘入史前（LLM 模仿上下文，防污染擴散）。
- 對應 feedback：新刻 `skill_filter_unit_matches_error_shape`；Adam 那句「鬆的背後一定有一個具體事件」直接就是改寫指令的規格——用戶的抱怨裡常常藏著完整規格。
