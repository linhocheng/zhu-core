# LESSONS 2026-07-09 · 知識庫/方法論上線＋孫武滿配

## L1：語域不同，embedding 就是對不上——「白話索引、原文呈現」
- 現象：孫子兵法入庫後，白話問「不用打仗讓敵人屈服」目標塊排 #15；text-embedding-004 對中文短句更慘（無關句 cos 0.90，甚至無關>相關）。
- 根因：兩層坍縮——模型層（004 中文短句擠在 0.8-0.97）＋語料層（整本書同主題，庫內 0.74-0.78 分不開）。
- 下次：跨語域檢索一律 gist 索引；gist prompt 三雷：①古語必須真的翻成大白話（模型會偷懶保留成語）②禁止同款開頭（全部「孫子說」= gist 之間又坍縮）③格式漂移用程式級寬容解析接住＋足額 max_tokens。
- 對應 feedback：skill_cross_register_retrieval_gist_index（今日新刻）、rrf_hybrid_retrieval_pitfalls。

## L2：門檻用猜的必漏水，用量的才站得住
- 現象：τ 初設 0.35（憑感覺），驗收時無關句照樣放行；量了真實分佈才知道 multilingual-002 的相關/無關分界在 0.68 附近。
- 根因：沙推不是驗證——「0.35 應該夠嚴」是腦內模擬不是數據。
- 下次：任何相似度門檻，先寫 calibration 腳本印真實 cosine 分佈（相關/擦邊/無關三組對照），看見縫隙才定值。lex rescue 同理：0.5 → 0.25 是算了真實 bigram 命中率（11 中 3 = 0.27）才調的。
- 對應 feedback：sandtable_not_validation。

## L3：方法論的正確生產模式是「問角色本人」
- 現象：問孫武「你會怎麼設計一套引導方法」，他一次給出 6 步含完成判準＋收手五條＋給問診者的戒律——比我們替他編的任何版本都完整且有靈魂。
- 根因：角色的 soul＋知識庫就位後，他對「自己的道怎麼運作」有一致的內部模型；設計權還給角色，結構化留給我們，authority 把關留給 Adam。
- 下次：共創三段式固定——角色設計（唯讀對話不落痕）→ 築翻 schema（triggerDesc 白話、步驟寫目標不寫台詞、收手織進步驟）→ Adam 過目才入庫（硬步驟）。
- 對應 feedback：soul_design_narrative_not_schema（同源：用角色能理解的話寫）。

## L4：SOP 的及格線是「小白築閉眼能跑」，大綱不是 SOP
- 現象：兩個 skill 初稿寫「用同款組裝跟角色對話」——對今天的我有意義，對沒有 context 的築是死路。
- 根因：知識的詛咒；寫的人腦裡有 session 記憶，讀的人沒有。
- 下次：skill 檔判準＝下一個什麼都不知道的築不用翻 code、不用查、不踩雷。做法：實戰驗證過的腳本原碼直接嵌入、環境地圖表格化、每顆雷寫進清單。Adam 的「閉上眼睛想像小白築」是好的自測儀式。
- 對應 feedback：hermes_self_sufficiency（讓接棒者不迷路是寫的人的責任）。

## L5：ailivex 語音斷句的套用點——收斂點不是 prompt
- 現象：Adam 要跟外部工程師說明「怎麼讓 TTS 不斷在怪地方」；翻出來發現全部設計釘在一個檔（agent/minimax_tts.py 的 _should_flush）。
- 根因（設計正確的原因）：斷句是確定性工作，釘在 LLM→TTS 唯一咽喉；只認句尾標點＋40字保險閥、換行折疊、首段 16 字特例、整段共用一條 WS session 保語調。
- 下次：向外轉述語音系統修法時，先講架構（串流 session vs 逐句獨立合成），再講規則——對方若是逐句打 API，改斷句救不回連貫感。
- 對應 feedback：deterministic_work_belongs_in_code、defend_at_convergence_point。
