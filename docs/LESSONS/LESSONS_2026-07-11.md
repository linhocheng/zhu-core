# LESSONS 2026-07-11 · 語音負載實測＋監控中台 Phase 1

## L1：真短板藏在「同時建線」，穩態併發是假想敵
- 現象：階梯實測 1→5 路 p50 全程平穩（3.9-4.4s），第 6 階 p95 卻暴衝 26.8s——但災難全部集中在開場 15 秒（6 通近乎同時建線，5 通首回合 23-27s），穩態馬上回落正常。
- 根因：每通新電話的建線（子行程＋載記憶＋首輪推理）是 CPU 尖刺，穩態通話反而便宜。沙推時所有人（包括我）都在算「同時講話幾路會爆」，沒人想到「同一秒打進來幾通會爆」。
- 下次：容量規劃必問兩個問題——「同時在線多少」和「進線速率多快」，兩個閘（總量＋斜率）都要設。任何「N 路沒問題」的宣稱要追問：是階梯慢慢加上去的 N，還是同一刻湧進來的 N？
- 對應 feedback：[[sandtable_not_validation]]——這條就是「實測推翻沙推」的最好標本。

## L2：本機網路通不代表通到目標 edge——測試基礎設施自己也要驗
- 現象：harness 在本機全綠（env/wav/RMS 自檢），一進房 signal timeout。Google 通、LiveKit 官網通，唯獨到我們的 LiveKit edge IP（161.115.163.x）TCP 超時。
- 根因：ISP 到特定 edge 的路由問題，跟程式零關係。差點往 token/SDK 方向鑽（都是錯的方向）。
- 下次：連線類故障先做三點定位（通用目標／同服務商別的端點／目標本體），三條 curl 一分鐘分清是我的碼、我的網、還是他的門。用戶回報「連不上」也先走這條。
- 對應 feedback：[[silent_failure_absent_log]] 的網路版。

## L3：合成通話會變成真記憶——測試隔離不是潔癖是必需
- 現象：cleanup 時發現 agent 從假通話裡抽了 14 筆「記憶」寫進 Firestore。
- 根因：agent 的收尾提煉不分真假通話（它也不該分——那是生產行為）。若當初圖省事掛在真角色下，14 筆垃圾記憶就混進真人格。
- 下次：任何會觸發生產寫入路徑的測試，先建專屬測試身份（user＋character），cleanup 腳本對齊 agent 會寫的每一個 collection，測完對賬（voiceSecondsUsed 2971s 就是對賬信號）。
- 對應 feedback：測試前列假設＋副作用分級（[[dryrun_before_test]]）。

## L4：nohup 之後 run.log 空的不等於沒在跑
- 現象：Adam 問「要往下了嗎」，run.log 0 bytes，差點誤判掛了。
- 根因：Python stdout 重導向後全緩衝；但結果 jsonl 是每階 open("a") 直寫——真相在資料檔不在 log。
- 下次：長跑腳本要嘛 `python -u`，要嘛把「進度真相」設計成直寫檔案；查進度看資料產出不看 stdout。

## L5：白皮書給「人＋AI」雙讀者時，機讀區要獨立成章
- 現象：Adam 要求白皮書要讓對方團隊的 AI 快速吃懂我們這套。
- 做法：第六章純 YAML（invariants/measured_numbers/gates/rules），人類章節講 why、機讀章節給 what；再附「最快路徑」順序清單當施工索引。
- 下次：跨團隊技術交接文件一律配機讀摘要區——對方的 AI 是真實讀者，別讓它從散文裡自己挖數字。

## L6：Vercel 上 void promise 寫入會無聲蒸發（監控事件脊椎實踩）
- 現象：writer 用 `void db.add().catch()`，本機必過；部署後 cron 回 200、Firestore 零筆、零錯誤 log。
- 根因：serverless 回應一送出 lambda 就凍結，沒 flush 的寫入直接死——這是「Cloud Run throttle 下無 fire-and-forget」天條的 Vercel 變體。
- 下次：回應後才要完成的工作一律走 `next/server after()`（可巢狀），包在共用 writer 內部 call site 零改動；驗證信號=DB 裡 doc 真長出，「路由回 200」對這個 bug 是零資訊。
- 對應 feedback：[[vercel-void-write-frozen]]（已刻新記憶）＋模稜兩可信號天條。

## L7：驗證要打「部署後的生產路徑」，自簽 cookie 是鑰匙
- 現象：變速箱寫側驗證需要 admin 身份，密碼不在我手上。
- 做法：拉 prod SESSION_SECRET → 照 auth-session.ts 格式自簽 admin cookie → 打真的生產 API 端到端（不是本機模擬 lib 呼叫）。42 秒完整一輪，每步讀 Cloud Run 真值。
- 下次：這招（escaped SA / SESSION_SECRET 自簽）是 ailivex 驗證的標準鑰匙；用完銷毀 cookie 檔。實彈前先跟 Adam 要授權（會產生分錢級費用＋碰生產開關）。

## L8：調節器類系統的三個結構決策（設計時就要定，不是寫完再補）
- 升快降慢的不對稱是刻意的（水位在門檻附近抖動→機器上上下下）；
- 「讀不到現場就不動作」是預設姿態（寧可不升不瞎動）；
- 任何鎖高檔的模式必須生而綁定到期＋自動回收（不然就是下一台殭屍燒錢機）。
- 家族：self-rescheduling loop 必綁 lifecycle 停止條件（同一條天條的變速箱版）。

## L9：middleware 401 和 route 401 是同一張臉（第三場）
- 現象：新 cron `/api/cron/ops-rollup` 帶正確 CRON_SECRET 仍 401，secret 反覆檢查沒錯
- 根因：middleware 登入牆先攔（PUBLIC_PATHS 沒加新路徑），回應 body 跟 route 自己的 401 一模一樣，肉眼分不出是哪層擋的
- 下次：加 cron 三件套（route+vercel.json+middleware 白名單）；被 401 先交叉驗證——同一把 secret 打已知會通的舊 cron，通=middleware 層，不通=secret 層。三分鐘定位
- 對應 feedback：interface-blood-vessel-check（cron 版）；新刻 new-cron-three-places

## L10：量測「出聲」要抓語意事件不是傳輸事件
- 現象：想量首音延遲，第一直覺是 TrackSubscribed（音軌訂閱到）
- 根因：agent 一進房就發布音軌，那時還沒開口——傳輸層事件（軌道接上）≠ 語意層事件（真的出聲）。用錯會嚴重低估
- 下次：LiveKit 用 ActiveSpeakersChanged（服務端算音量）；通則=量用戶體感時，找「用戶感知得到」的信號，不是「系統準備好」的信號
- 對應 feedback：ambiguous-signal-not-proof 的量測版——TrackSubscribed 之於「出聲」也是模稜兩可信號

## L11：計費錶接上第一天就回本
- 現象：billable_instance_time 儀表化後第一眼：doc-worker 24h 燒 14.2 實例時、v17 名義冷備卻有 6.4、loadtest 殘留 0.5
- 根因：沒有計費面的持續可見性，設定面的「已降 0/已冷備」就是唯一敘事——三面分離的認知偏差每天都在發生，只是沒儀表就看不見
- 下次：這三個異常是明天的第一批工單；任何「已關/已降」的宣告從此有了常設對賬面
- 對應 feedback：cost-verify-billing-meter-not-config（從單次驗證升級為常設儀表）

## L9：驗收表量什麼就只保證什麼——量錯維度會全綠（podcast duo 第四場）
- 現象：duo 協議管線把舊病全治好（位移 0→4、假讓步歸零、問號乒乓 90%→17%），我發了七綠一紅的成績單慶祝；Adam 一讀稿就抓出兩個新病：協議洩漏（「我接」「我保留的是」滿場）、抽象逃逸（燒/能量/接住）。我的儀表上根本沒有這兩個病的刻度。
- 根因：驗收指標繼承自「治辯論機器」的規格書 v1，只量收斂不量語感。修好 A 病的機制（內部欄位＋協議 prompt）正是 B 病（報告腔）的病原。
- 下次：交付「生成內容」類系統時，驗收表必須有一軸是「產出讀起來像不像該像的東西」——而且要用敵意的眼睛讀原文，不能只看數字。數字全綠+沒讀稿=沒驗。
- 對應 feedback：[[ambiguous_signal_not_proof]] 的變體——「我的指標全過」對「沒量到的病」是零資訊。

## L10：封詞是打地鼠，規則要寫在動作層（Voice Layer 核心）
- 現象：驗出「我接。但」後我第一反應是加 regex 封那個詞——Adam 的規格書第一句就點名這是錯層：封「我接」它長出「我收下」。實測 judge 第一集就抓到 10 條種子正則抓不到的變體。
- 根因：詞是動作的表面形狀。真正的規則是「不准報告你的對話動作」（move 層級），詞庫只能當偵測器的加速快取，且要自成長（Layer 2 命中→寫回 Layer 1）。
- 下次：任何「輸出品質」規則先問：我是在禁一個詞，還是在禁一個生成動作？禁詞的修法一律升格到動作層再落地。
- 對應 feedback：[[filter_unit_matches_error_shape]] 的深化——攔截單位不只要對齊錯誤形狀，還要對齊錯誤的生成機制。

## L11：協議洩漏的病根是同一口氣生成；規則文本自己也會漏
- 現象：history 明明只回灌 utterance（P2 本來就對），角色照樣滿嘴協議腔；「假設一個情境」是我在 prompt 裡教的原話，角色一字不差照唸還被我當成 R4 守住的證據。
- 根因：思考（heard/stance/cost）和台詞在同一次生成裡寫出來，台詞被剛寫完的格式污染（P1）；模型模仿 context 裡的一切形狀，包括規則裡的範例句和幕指令的條列格式。
- 下次：內部思考和對外說話必須是兩次獨立生成，思考只以「結論」傳入說話 pass；prompt 裡給角色看的每一句範例文字都要當成「他會照唸」來寫。
- 對應：拆分實測 MOVE 命中 26→0，這是今天最大的單刀。

## L12：偵測器需要調音量；量尺自己也會犯它在抓的病
- 現象：Phase B 偵測器全開後 Adam 一讀：「修過頭了」——退回壓力讓角色過度自我審查，話像在躲地雷。同時我的驗收正則把「說出口」（動詞、可觀察行為）誤判成「沒有出口」（隱喻），把「引用對方原話往下挖」誤判成蓋章複述——量尺犯了 BUG-B。
- 根因：風格類規則的執法強度本身是個旋鈕，不是越嚴越好；正則量尺沒有語境。
- 下次：風格砂紙只磨一遍（重講一次就放行）、judge 判準明文「拿不準就 pass，寧可放過交給詞庫學」；發布任何量尺前先拿它掃一份已知的好稿，看它冤枉誰。
- 對應 feedback：[[technical_honesty_over_smoothness]]——「指標退步」要先驗量尺再認病。

## L13：平行築 session 同 repo 施工——commit 會掃走對方的未提交檔案（雙方都要看）
- 現象：今天 AIR 上兩個築 session 同時在 ailivex-platform 施工（一線監控/首音延遲，一線 podcast duo/Voice Layer）。第三場的 v18.7.0 commit 把第四場所有未提交的 duo 檔案一起收進去——commit 訊息只寫首音量測，內容卻含整條 podcast 管線，訊息與內容分裂且已推不能改寫（v18.7.1 已加考古註記補救）。
- 根因：git add 慣性（add -A / add 整目錄）看到什麼收什麼；兩個 session 互不知道對方存在。
- 下次（規約，雙方遵守）：① commit 前 `git status` 看到**不是自己改的檔案**→先停，問 Adam 或只 add 自己的檔案清單；② 開工第一件事 `git pull`＋看最新 commit 是不是自己認識的；③ 有雙線開工時 Adam 或任一方在 ZHU_LAST_WORDS 標明「另一線正在跑＋戰場範圍」；④ 盡量分目錄施工。
- 對應 feedback：[[compacted_session_verify_state]] 家族——別的 session 也是「別處」，現場會被別人動。
