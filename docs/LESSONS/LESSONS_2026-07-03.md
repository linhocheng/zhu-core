# LESSONS 2026-07-03 · ailiveX 記憶系統四批強化（+ 前夜 UDN 健檢）

## L1：純 cosine 對長篇敘事記憶去重會連環誤殺——真重複的鑑別特徵是「逐字相似」
- 現象：0.85 純 cosine 誤殺 75 筆（「牧羊人的奇幻之旅」被「用戶叫 Adam」吸走）；升 0.92＋同 type **仍誤殺**（「牧羊人」被「咖啡館手沖」吸走）。同一對人的長篇親密敘事，embedding 天生擠在同一區。
- 根因：cosine 度量的是「語域＋人物＋主題」的整體相似，不是「同一事件」。真重複（同一次萃取寫兩份）必然逐字級相似。
- 下次：語義去重一律**雙門檻**：cosine ≥ 0.9 **AND** CJK bigram 重疊 ≥ 0.5（以較短者為分母）。批次清理前先抽樣人工驗證；永不硬刪（archive + dedupOf 可回溯）——紅線這次立大功，兩輪誤殺全數救回。
- 對應 feedback：`skill_filter_unit_matches_error_shape` 的姐妹課——過濾的單位要對齊錯誤形狀，去重的門檻要對齊重複的本質。

## L2：鏡像實作的腐敗是漸進的——「兩邊都有這功能」不等於「兩邊行為一致」
- 現象：TS memory.ts 和 Python firestore_loader 名義上是鏡像，實際審計出 15 項不一致；最毒的是 Python 讀函數少回 3 個欄位，讓下游 stale/active-recall/時間感整段變成「看起來有邏輯的死碼」——沒有報錯，只是靜默不生效。
- 根因：每次只改一邊「順手」，沒有對照表逼自己逐項驗。
- 下次：跨語言鏡像模組要維護**對照表**（欄位、參數、門檻逐項），改動時打勾；懷疑死碼時先查「上游真的有給這個欄位嗎」。
- 對應 feedback：`feedback_dialogue_voice_stream_parity` 的規模化版本。

## L3：資料體檢先於機制審計——現場分佈一小時內照出所有謊言
- 現象：機制審計要兩個 agent 各 15 分鐘；而一支直接掃 Firestore 的腳本（tier/status/type/hitCount/embedding 分佈）幾分鐘就把「status 全空、embedding 24/149、hitCount 凍 0、importance 全擠 5」全部照出來——機制報告只是解釋了資料已經證明的事。
- 下次：審「系統有沒有在運作」先跑資料分佈統計，再讀 code。欄位分佈異常（全空/全同值/全 0）＝該機制死亡的直接證據。
- 對應 feedback：三段公式「看現場」的資料庫版。

## L4：（前夜 UDN）同一個天條可以在同一天、修對之後、換個殼再犯
- 現象：早上把 ailivex podcast 的 CPU throttle 修對（worker 三旗標），晚上在 UDN 主平台寫「dispatch fire-and-forget 呼叫自己 + abort」——同一個病，換了「呼叫自己」的殼就沒認出來。
- 根因：學到的是「worker 要開旗標」（解法形狀），不是「throttled service 上不存在背景工作」（病的本質）。
- 下次：刻教訓時刻**病的本質**不是解法的形狀；新代碼動手前問「這裡有沒有『回應後還要繼續算』的地方？」
- 對應：已升天條（CLAUDE.md）。

## L5：交付「規範」給下一棒時，踩雷紀錄比設計圖值錢
- 現象：白皮書寫到 §8 才意識到：接手工程師照 §1-§7 抄一遍大概率會在同樣的地方摔（純 cosine、兩路徑分裂、SIGKILL），因為那些設計「看起來顯然正確」。
- 下次：所有 handoff 文件必含「踩雷紀錄」章節，每條寫清楚「為什麼直覺做法會錯」；checklist 尾端放終極鑑別信號（能一票驗證整個系統的那個測試）。
