# LESSONS 2026-07-04 · UDN 產品化改版 + ailiveX soulCore 退役

## L1：讀取優先序 + 雙欄位 = 「編輯不生效」的靜默病
- 現象：ailiveX 角色有 soul + soulCore 兩欄，讀取 soulCore 優先。Adam 以為自己「都直接用最終靈魂檔案」，實際上吳念真一直用 540 字舊摘要在演（完整版 2,499 字躺在 soul 被忽略）、Echo 用半套。他改 soul 沒感覺變好，因為根本沒生效。
- 根因：真相分裂（兩份即是零份）的變體——不是兩份不同步，是「使用者以為的那份」不是「系統讀的那份」。UI 還把兩個 textarea 並排，加劇混淆。
- 下次：任何「A 優先 fallback B」的雙欄位設計，要嘛 UI 只暴露生效的那份，要嘛合併。診斷手法：欄位長度對比表（soul vs soulCore 字數）幾分鐘照出所有分裂，比讀代碼快。
- 對應 feedback：破綻三處之「真相分裂」；`feedback_diagnosis_verify_before_write`（先查資料再下結論）。

## L2：資料層修法可以讓「已部署的舊代碼」立即改行為——fallback 鏈當遷移工具
- 現象：v15 語音 agent 讀 `soulCore or soul`，已部署的 image 改不了代碼。但把 Firestore 的 soulCore 欄位刪掉，舊代碼自動 fallback 到 soul——不用重部署，線上行為即刻修正。
- 下次：修「讀取優先序」類問題時，先問「能不能在資料層動手讓所有版本一起吃到」，比逐版本重部署快且零風險。前提：fallback 鏈存在且指向正確的欄位。
- 對應：Cloud Run 版本隔離紀律的補充——資料 schema 是所有版本的共用面，動它=動全部。

## L3：「UI 打不進去」的診斷階梯 + 指紋
- 現象：別名欄位疑似無法輸入。診斷順序：①資料形狀（aliases 若是 string，`join()` 直接炸掉整個 modal）②靜態讀碼（controlled component 的 join/split 迴路、remount 陷阱）③真瀏覽器重現。這次走到 ③ 建好環境時 Adam 喊停。
- 帶走的指紋：**「腳本種的資料有值、手動輸入的全是空」= UI 輸入鏈斷掉的特徵**（聖嚴/星雲/達賴的別名是當年腳本寫的，手動編輯過的角色全空）。
- 另外重現環境三顆雷排掉：.env.local SA JSON 真換行（系統 env 蓋掉）、殘留 dev 進程佔 port（lsof -ti 殺）、不猜生產密碼——無狀態 HMAC session 用 SESSION_SECRET 自己簽一張 cookie 進場。
- 對應 feedback：`feedback_env_literal_newline_url`、`skill_local_replay_over_remote_wait`。

## L4：付費 API 餘額臨界的症狀是「間歇性慢」不是「全死」
- 現象：Adam 回報「v15 福哥反應有點慢」，體感是慢。真相：Anthropic 付費 key 餘額見底，請求有的過、有的 400 被拒——被拒那輪角色沒聲音，用戶等一等再講，下一輪過了才有回應，體感就是「慢」。
- 下次：語音「變慢」先查 log 的 4xx 分佈再查性能。餘額臨界（不是歸零）的指紋：同一通話裡部分輪次成功部分 400。
- 對應：天條「模稜兩可信號不能當成功證據」的鏡像——「慢」這個模糊症狀也不能直接當性能問題，先找鑑別信號。

## L5：「你是不是誤會了什麼」是最便宜的糾偏——中途回報要讓 Adam 有插話點
- 現象：別名 bug 我按自己的理解（編輯視窗打不了字）直接開重現工程，燒了好幾輪環境雷。Adam 一句話喊停，原來問題沒那麼嚴重。
- 根因：接到模糊回報（「好像無法輸入」）時沒先花一句話跟 Adam 對齊症狀就開工。跟 Tracy 天條「好奇先於防衛」同構：好奇先於開工。
- 下次：模糊 bug 回報 → 先一句話複述我理解的症狀＋問「是這個嗎」，再決定要不要起重機。
- 對應 feedback：`feedback_ask_plain_language`、`feedback_clarify_before_execute`。

## （晚場補記 · ailiveX 檢索與計費）

## L-A：RRF 並列陷阱——0 分文件照排名給分會反壓真命中
- 現象：episodic 檢索改 RRF 後專名 query 還是撈不到；debug 印分數才看到 BM25 全 0 的文件拿到第 1、2 名的 rank 貢獻
- 根因：rankOf 對並列 0 分照 sort 順序發名次；標準 RRF 語義是「沒被該檢索器撈到＝無貢獻」，自己實作時漏了這層
- 下次：任何 rank-based 融合，先問「0 分/未命中的 rank 怎麼算」；驗證用「只有做對才會出現的信號」（專名 query 命中對應記憶）
- 對應 feedback：模稜兩可信號≠成功證據（「兩組不同」過了但專名測試沒過，才抓到）

## L-B：加法混合計分救不了 cosine 坍縮，rank-based 才免疫
- 現象：照白皮書 cosine×0.7+詞彙×0.3 實測失敗——窄域無關記憶 cos 飆 0.86，0.3 權重蓋不過
- 根因：加法計分吃絕對值，坍縮讓絕對值失去鑑別力；RRF 只看名次天生免疫。repo 裡 knowledge-search 早就用 RRF（BM25:cos=2:1），同 repo 已驗證的解法先抄
- 下次：移植設計規範前先跑一次真實資料驗證（這次驗了才沒把壞計分上線）；「白皮書寫的」也要過現場
- 對應 feedback：沙推不是驗證（正例——這次先驗再上）

## L-C：計費防呆的真正破口是「空房繼續燒」不是「掛斷沒存」
- 現象：稽核 agent 計費時發現用戶離房後 agent 留在房裡等 LiveKit 空房超時，期間照計費且 flush 延遲
- 根因：v15 沒有任何 participant 離房處理；掛斷/重整/斷網對 server 是同一個事件（human participant leaves），這一個 hook 收掉三種 case
- 下次：計量系統先畫「誰離開時錢還在走」的時序圖再寫码；crash 漏計方向要設計成「少算」（對用戶有利）
- 對應 feedback：介面建完強制問血管接通了嗎（計費的血管是離房事件）

## L-D：開藥單前先盤點——「缺 resolved 機制」其實已存在
- 現象：對標白皮書列 P1 說缺 resolved，深挖後發現 promise-reflection 已上線且比白皮書版完整
- 根因：拿 checklist 對表時只看欄位名（status/resolved），沒看同語義的既有機制（fulfilled/promise-reflection）
- 下次：gap 分析先按「語義」找對應物再判缺席；診斷報告過重會浪費接下來的施工排程
- 對應 feedback：寫架構診斷前必先核 code + 既有記憶
