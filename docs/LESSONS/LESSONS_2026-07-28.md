# LESSONS 2026-07-28 · /talk 撥號盤 LCD 訊息卡死修復（v18.24.1）

### L1：蓋住畫面的訊息，寫入時就要指定誰負責清除
- 現象：/talk 空號碼撥號後鍵盤看似全死；真因是錯誤訊息 `lcdMsg` 永遠優先顯示、無人清除，輸入其實都有效
- 根因：昨天測了「錯誤 → 顯示訊息」的正向路徑，沒測「顯示訊息之後，用戶的下一步」。單向旗標（只有 set 沒有 clear）是狀態機斷頭路
- 下次：任何會覆蓋主顯示的 message state，寫 `setX(msg)` 的同一刻回答「誰、在什麼互動上把它清掉」；驗收劇本要包含「從錯誤狀態走回正常」這一步
- 對應 feedback：interface_blood_vessel_check（誰讀/何時讀/沒讀怎樣——這次是「誰清/何時清/不清怎樣」）

### L1：harness 背景任務會砍掉長跑 worker——nohup 脫鉤是唯一正姿（記憶二踩實錄）
現象：`npm run worker` 用 harness 背景跑，20 分鐘後被 harness 收掉，monitor job 卡 running、312 筆殘批。
根因：harness 管理的背景進程生命週期不歸我控；[[skill_detached_relay_nohup_monitor]] 記憶早就寫了，第一次沒用。
下次：本機長跑一律 `nohup … & disown` 落地成反射；斷批復原 SOP＝收屍 job＋清殘批（runs 不冪等）＋新 batchId 重跑，已刻進 TITAN_BASELINE 技術教訓節。
對應 feedback：[[skill_detached_relay_nohup_monitor]]、[[feedback_framework_vs_reflex]]。

### L2：競品情報以登入後產品為準，行銷頁是誘餌場
現象：/attribution 判「無歸因功能」，Adam 登入後側欄就有「AI 導流歸因」模組，差點把錯誤定位寫進戰略。
根因：行銷頁是 SEO 關鍵字著陸頁（他們自己就在做 GEO），功能地圖只有產品內側欄是真的。
下次：競品偵察必分兩層——行銷面（定位話術）與產品面（真功能），結論標注來源層；能實操就實操。
對應 feedback：[[feedback_ambiguous_signal_not_proof]]（情報版：頁面存在≠功能存在）。

### L1：Firestore 組合查詢（where＋orderBy 另一欄）要 composite index——production 首日炸頁
現象：/today 通知查詢 `where('readAt','==',null).orderBy('createdAt','desc')` 上線即 FAILED_PRECONDITION，整頁黑掉只剩錯誤字串。
根因：composite index 雷記憶裡有（findNearest 版），但 where+orderBy 變體長相不同就沒認出來；上線前沒在 production 資料形狀下真點過那頁。
下次：組合查詢＝「兩個不同欄位同時出現在查詢鏈」就過 index 檢查；小集合正解是拆查詢＋記憶體排序（不帶 orderBy 就不 limit）；新頁上線後第一件事是真點一次。
對應 feedback：[[reference_firestore_vector_search]]（已補變體）、[[feedback_framework_vs_reflex]]。

### L2：接了管子的成功碼不是成功碼
現象：deploy.sh 半路死在 scheduler 步驟，背景任務回報 exit 0——pipe 尾端 tail 的退出碼。
根因：`cmd | tail` 的 exit code 是 tail 的；長腳本背景跑接管子＝自廢鑑別信號。
下次：背景長腳本不接管子（輸出落檔事後讀尾）；收案看每步成功輸出行。
對應 feedback：[[feedback_pipe_eats_exit_code]]（本場新立）、[[feedback_ambiguous_signal_not_proof]]。

### L3：gcloud scheduler create/update 旗標不對稱——部署腳本裡的無聲慣性斷點
現象：`--headers` 只有 create 吃，update 要 `--update-headers`；deploy.sh 每次全量部署最後一步都在無聲失敗。
根因：同一條指令的 create/update 路徑旗標集不同，寫腳本時只驗過 create 路。
下次：冪等腳本的「存在就 update」分支要兩條路都真跑過一次才算驗證；家族同 [[feedback_manual_cloud_change_sync_deploy_script]]（部署腳本是未來的現場）。

### L1：deploy.sh 子命令部署 ≠ 部署了你的 code——「新 revision」和「新內容」是兩件事
現象：`./deploy.sh admin` 跑完 exit 0、revision 換新號、100% 流量，但線上 CSS 沒有新 class——它只把 Artifact Registry 的舊 :latest 重新上架，build 是獨立步驟。
根因：子命令語意（上架）與心智模型（部署我的改動）不一致；exit 0 與新 revision 都是模稜兩可信號。
下次：改 code 後一律 `build`＋`admin`；收案用 digest 證據鏈（build 產出 digest == revision imageDigest）；本機 CSS hash 可當探針、JS chunk hash 本機≠Docker 不可用。腳本已加 echo 護欄。
對應 feedback：[[feedback_ambiguous_signal_not_proof]]、[[feedback_pipe_eats_exit_code]]（同日孿生）。

### L2：同一顆按鈕對兩個欄位兩種脾氣＝資料丟失雷
現象：GEO「AI 重新研究＋補題」對題庫是去重追加（按鈕也這樣寫），對競品是整包覆蓋——手改的競品清單會被無聲洗掉。
根因：兩條寫回路徑各自實作，合併語意沒有全鈕統一；UI 只描述了其中一種脾氣。
下次：一顆按鈕動多個欄位時，逐欄位問「覆蓋還是合併」，語意不一致就是雷；修法統一成合併（既有保留、新增追加）。已入藍圖十二章「一鈕一律」。
對應 feedback：[[feedback_default_switch_standing_instance]]（家族：寫回語意不對齊）。

### L3：UI 文案是承重牆——文案與機制真相分裂＝假文案
現象：病歷頁寫「免登入，拿到連結即可觀看」，實際上設通關碼後整個客戶入口都要碼。
根因：門禁機制後來升級（v2.4 通關碼），文案停在舊真相沒人回頭改——文案沒有 pinning test。
下次：寫任何描述機制的 UI 文案前，先去機制現場驗證那句話今天還真不真；機制改動的 checklist 要含「掃描描述它的文案」。
對應 feedback：[[feedback_backend_client_must_sync]]（文案版）、藍圖承重牆帳（prose-pinned 的極端例）。
